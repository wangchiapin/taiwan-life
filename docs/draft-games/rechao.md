## 劇情

Ami 和兩個朋友晚上要去熱炒店吃飯，Ami 會晚一點到，用 LINE 請玩家（主角）先去點菜。一共四個人（主角、Ami、兩個朋友）。Ami 交代三道菜（各一盤）和先拿幾瓶台啤（四或六瓶）；吃到一半 Ami 傳訊息要「加點」一盤菜和兩或三瓶啤酒；吃飽以後主角去櫃檯結帳：啤酒「喝幾瓶算幾瓶，沒開的可以退」，要核對帳單、付錢、核對找的錢。最後傳訊息給 Ami。
（總清單重點「多人點菜、加點、啤酒怎麼算、結帳時核對帳單」。）

## 關卡流程（ORDER）

START → SEAT（說「四位」）→ **ORDER（點三道菜，先記下來）** → **BEER（先拿幾瓶啤酒，先記下來）** → **CONFIRM（老闆娘複誦，45% 說錯）** → **SERVE（菜上桌，40% 端錯成沒點的菜）** → **ADD（Ami 傳訊息加點，實際說的先記下來）** → **RETURN（算啤酒：喝幾瓶算幾瓶，先記下來）** → **PAY（帳單報價，45% 多算）** → PAY_FIX（多算被抓到後重新付錢）→ **CHANGE（找錢，40% 找錯）** → END → RESULT。

## 對方出錯點與機率

| 關卡 | 錯誤機率 | 怎麼出錯 | 正解 |
|---|---|---|---|
| CONFIRM | 45% | 複誦時把其中一道菜換成別道，或啤酒瓶數多／少兩瓶（各一半） | 沒錯→「對，沒錯，謝謝。」；錯→「不好意思，我們點的是…，啤酒…瓶。」 |
| SERVE | 40% | 端來一道你們沒點的菜（上錯桌） | 沒錯→「好，謝謝。」；錯→「不好意思，這道○○我們沒有點。」 |
| PAY | 45% | 帳單多算一盤沒點的菜，或多算一瓶沒開的啤酒（帳單上看得到那一行） | 沒錯→「給你○元。」；錯→「不好意思，好像算錯了，應該是○元吧？」 |
| CHANGE | 40% | 找的錢多或少十或二十元 | 沒錯→「好，謝謝。」；錯→「不好意思，好像找錯了，應該找○元吧？」 |

CONFIRM、SERVE、PAY、CHANGE 都用共用的 `catchState`／`payStates`：①沒錯／謝謝　②有禮貌指出問題（對方沒錯時，數字或菜名是錯的）　③沒禮貌（永遠錯）。抓到錯之後老闆娘道歉並補救（改正複誦、把菜端走換對的、重算帳單、補找錢）。
**ORDER、BEER、ADD、RETURN 是「先記下來」的關卡**：玩家說錯會扣十分（寫進錯誤紀錄），但不擋住，遊戲照他「實際說的」往下走（複誦、上菜、帳單都用實際點的算）。SEAT 是固定正解、選錯留在原關。

## 價錢與計算邏輯

- 菜單：菜脯蛋 100、炒空心菜 100、客家小炒 180、鹽酥蝦 220、三杯雞 250、蔥爆牛肉 260；台啤一瓶 80（都是常見範圍，**待確認**）。
- 實際應付 `t.total` ＝（實際點的菜＋實際加點的菜）的價錢加總＋ `t.billBeer` × 80。`t.billBeer` 是玩家在 RETURN 關**實際說的啤酒瓶數**（照實說＝喝掉的瓶數）。
- 桌上情況：實際喝掉 `t.drunk` ＝ min（實際拿的瓶數 − 1，Ami 要的瓶數 − 1）；至少剩一瓶沒開（`t.unopened`），所以「沒開的不用算」一定用得到。
- 報價 `t.said` ＝總價，或總價加上沒點的一盤菜／沒開的一瓶酒的價錢（共用 `initPay`）；帳單畫面（PAY 關）列出每一道菜和啤酒，多算的那一行也列在上面，玩家要自己對。抓到錯以後（PAY_FIX、CHANGE）畫面改成正確的帳單。
- 你給的鈔票 `billFor(n)`：≤500 給 500、≤1000 給 1000、≤1500 給 1500、其他 2000；找零 `t.change` ＝ 鈔票 − 總價，實際找的 `t.given` 可能差十或二十元。

## 正解怎麼判定

好結局＝錯誤 ≤ 2 次，**而且最後實際點到的菜、啤酒、加點，和 Ami 要的完全一樣，帳單上的啤酒瓶數＝實際喝掉的瓶數**（`t._orderOK && t._beerOK`）。所以玩家在 ORDER／BEER／ADD／RETURN 說錯，即使其他都對，也是壞結局，Ami 會說「菜／啤酒好像和我說的不一樣」或「啤酒的錢好像算錯了」。
